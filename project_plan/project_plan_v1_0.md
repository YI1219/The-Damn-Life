# The Damn Life 项目计划书 V1.0

> 制定日期：2026-03-28  
> 依据：仓库内 `docs/`、`project_target/`、`project_plan/0.5_env_plan.md` 与当前代码实现状态；外部分析基于公开资料与常见开源生态（具体 star 数等以各仓库实时页面为准）。

---

## 1. 执行摘要

**结论**：项目方向（离线优先、可审批、可审计的个人自动化助手 + Skill 运行时）在 2026 年仍具差异化价值，但需在「环境管理器」层尽快补齐 **真实语言理解/规划**、**Skill 契约与隔离**、**可分发安装形态**，否则易被通用 Agent 框架 + 脚本组合替代。

**V1.0 战略焦点**：在 V0.5 已验证的「配对 → 计划 → 审批 → 执行 → 审计」闭环上，把 **环境管理器** 做成可扩展内核，并明确与专利路线的关系（软件与光计算硬件为两条线，除非公司有硬件产品化路径）。

### 1.1 工程原则：极小依赖、极致效率、AI 原生开发

项目将 **分发体积、冷启动、常驻内存、依赖扇出** 视为与「隐私、审批、审计」并列的长期卖点，而不是事后优化项。

1. **依赖纪律（核心路径）**  
   环境管理器、传输协议、持久化与任务状态机等 **主干** 优先采用 **标准库 + 少量可审计依赖**。新增依赖须满足可陈述的收益（例如不可替代的协议实现、安全边界），并记录：用途、替代方案为何放弃、移除条件。

2. **效率可验收**  
   为宿主进程、安装包、移动端构建物设定 **预算指标**（例如二进制/包体上限、启动时延、空闲内存），在 CI 或 release 流程中做 **回归对比**，避免「框架堆叠型」膨胀。

3. **面向 AI 的代码形态**  
   不追求「未经训练的读者也能轻松读完所有实现」。优先保证：**模块边界清晰、契约稳定（类型、schema、协议版本）、测试与 gate 可自动执行**，使人类主要负责安全与架构决策，细节迭代可由 AI 辅助完成。对外与对贡献者仍以 **契约文档 + 关键路径注释** 为主，而非全文教程化。

4. **必要权衡**  
   极小依赖可能增加自研成本；「非全民可读」须用 **测试覆盖、审计与安全敏感路径的人工可读性** 兜底，避免关键权限与解析逻辑变成不可审查黑箱。

## 2. 当前目标、计划与进度（梳理）

### 2.1 三层目标（并存，需对齐）

| 层级 | 来源 | 核心表述 |
|------|------|----------|
| 愿景/长期 | `project_plan/0.5_env_plan.md` | 自然语言控机、隐私本地、手机遥控（含 P2P 愿景）、浏览器与全界面理解 |
| V0.5 产品边界 | `project_target/project_target_v0_5.md`、`docs/mvp_scope_v0_5.md` | 单机、离线优先、Skill Runtime 最小集、任务闭环、明确推迟多设备/P2P/市场 |
| 代码/README 现状 | `README.md`、`host/` | 单机闭环 demo：WebSocket 配对、SQLite、文件整理 Skill、审计与 weekly gate |

### 2.2 计划文档之间的关系

- **`0.5_env_plan.md`**：偏完整产品叙事与 16 周路线图（含 WebRTC、扩展、多 Skill 等），体量大于当前 MVP 冻结范围。
- **`mvp_scope_v0_5.md`**：正式 **范围冻结**，防止蔓延；与代码验收一致。
- **`project_target_v0_5.md`**：与冻结范围一致的「目标说明书」，并强调 **环境管理器 + 本地模型 + Skill 规范**。

### 2.3 实际进度（相对文档的诚实对照）

**已对齐冻结范围的成果（高置信）**：

- 连接与配对码生命周期、心跳与在线状态（见 `host/src/server.ts`）。
- 任务状态机与审批后再执行、失败时可解释建议。
- 文件整理 Skill 与结构化结果、审计事件写入。
- Weekly demo gate 定义（`docs/weekly_demo_gate.md`）及对应 npm 脚本入口。

**与 `project_target_v0_5.md` 仍存在的缺口**：

- **本地大模型对话与规划**：当前 `planner.ts` 为关键词规则，非通用 NL→计划；尚未体现「可切换本地推理后端」。
- **Skill 清单级权限模型**：代码中为宿主内路径白名单；尚未达到 manifest 级多维权限 + 用户可配置策略的产品形态。
- **运行隔离**：文档建议 Docker/WASM 等；当前 Python Skill 为直接子进程级调用，需演进。
- **一键安装包 / 桌面壳**：仍为开发者 `npm run dev` 形态。

## 3. 与 `project_target/patent_1.md` 的同步分析

### 3.1 专利内容概要

`patent_1.md` 描述的是 **全光大模型计算系统**：多芯光纤空间分复用、权重在光路中循环、微环阵列光计算、色散与信号整形、温漂时序校准等，属于 **AI 推理硬件/光计算** 领域。

### 3.2 与 The Damn Life（软件）的关系

- **技术栈无直接重叠**：当前仓库是编排层、Skill、移动端 UI、SQLite 审计，不涉及光器件或片上光计算。
- **商业/IP 关系**：可作为公司 **第二条能力线**（硬件加速推理）储备；若未来「环境管理器」要调度 **本地光计算推理后端**，可在架构上预留 **推理后端抽象接口**（与今日调度本地 Ollama/vLLM 同类）。
- **申请与产品叙事**：对外产品故事应区分「个人自动化与可信执行环境」与「光学推理加速器」，避免投资人/用户误以为 MVP 依赖未量产硬件。

## 4. 竞品与类似开源/市场格局（定性）

> 下列项目定位来自公开描述；具体指标请以 GitHub/Product Hunt 等实时页面为准。

| 类型 | 代表方向 | 与我们的关系 |
|------|----------|----------------|
| 本地 NL→代码/命令 | Open Interpreter 等 | 功能重叠高；普遍强在执行与生态，弱在「消费级审批/审计/Skill 打包规范」的一体化 |
| IDE/开发者 Agent | Cursor、Codex、各类 agent 框架 | 强在写代码；非「手机控家用电脑 + 非技术用户」场景 |
| 自托管「一个机器人连 Telegram/WhatsApp」类 | 多种开源/发行版（名称与热度变化快） | 渠道多、上手快；往往弱在结构化审计、细粒度文件白名单、可撤销副作用设计 |
| 系统自动化 | Shortcuts、Power Automate、RPA | 成熟但模型与「对话式全权代理」路径不同 |
| 浏览器自动化 | Playwright/Puppeteer + 自研 agent | 与「动态网页」故事重叠；需与安全模型结合 |

**我们的可辩护优势（若坚持做到位）**：

- **人机在环**：高风险默认审批 + 审计时间线，偏「可信个人操作系统」而非「自动跑脚本」。
- **Skill 作为可分发单元**：长期可形成与 CLI/浏览器/文件系统的统一契约（若规范落地）。
- **单机离线闭环**：与强云依赖方案区分（需在产品中真正接上本地模型）。
- **极轻技术栈**：相对「全家桶框架」型助手，更小安装体积、更快启动与更低常驻开销，与本地常驻型产品形态一致（见 §1.1）。

**主要缺陷（当前）**：

- 规划层过简，**泛化 NL 能力不足**，易被「通用 agent + 几条 prompt」替代。
- 尚未形成 **安装即用的终端用户包** 与 **多 Skill 市场/目录**（虽 V0.5 刻意不做市场，但要有技术预留）。
- 浏览器、P2P、多设备均在文档愿景中，**代码未跟上的部分**会削弱差异化叙事。

## 6. 是否值得继续做？如何开展（尤其环境管理器）

### 6.1 价值判断

**值得**，条件是把差异化做成 **默认体验** 而非文档承诺：

1. **可信执行与审计** 与 **自然语言** 同时成立；  
2. **环境管理器** 成为稳定 SDK：第三方 Skill 只靠 manifest + 沙箱边界就能接入；  
3. 至少一条 **非演示级** 场景（文件整理已起步）+ **日程/应用启动** 等第二场景，形成日常习惯。

若长期停留在「关键词 planner + 单 Skill」，则边际价值下降快。

### 6.2 环境管理器（V1.0 定义加强）

对照 `project_target` 中的定义，**环境管理器**在 V1.0 应明确交付：

1. **会话与设备**：保留配对与连接抽象，为 V1 局域网预留接口。  
2. **规划器插件化**：规则 planner + **本地/远程 LLM planner** 可切换，输出统一为 **JSON TaskPlan（schema 校验）**。  
3. **策略引擎**：默认拒绝；按 Skill、路径、操作类型（读/写/删/网络）判定是否需审批。  
4. **Skill 运行时**：manifest（权限声明、schema、版本）→ 子进程/Docker（二选一优先落地）→ 结构化 stdout/文件结果 → 审计。  
5. **推理后端抽象**：`LocalLlmProvider` 接口（如 Ollama HTTP），便于日后接自研或光学推理后端。  
6. **数据生命周期**：一键清除、导出审计、可选加密备份。

## 7. V1.0 路线图（里程碑）

### Phase A：内核硬化（约 4–6 周）

- TaskPlan JSON Schema 固定版本；planner 实现 **LLM 实现 + 规则 fallback**（离线可用路径清晰）。  
- Skill manifest v1 与宿主校验；第二个内置 Skill（建议：**应用启动/打开 URL** 或 **最小日程提醒**）。  
- 审计模型扩展：记录 planner 版本、模型 id、权限决策。  
- Windows 优先的安装文档或简易打包（如 `pkg`/`electron`/`tauri` 择一最小试点）。

### Phase B：体验与信任（约 4–6 周）

- 移动端：计划预览、风险标签、审批理由展示优化。  
- 撤销：对「移动/重命名」类操作做事务日志或可逆映射。  
- 可选：接入 **cognee** 类库的「本地知识库」模式（仅索引显式目录）。  
- 技术 spike：**Lightpanda** 驱动的一个只读「抓取当前页正文」原型（含权限开关）。

### Phase C：生态接口（约 4–6 周，与 V1.0 发布候选）

- Skill SDK 文档 + 1 个第三方示例 Skill。  
- 评估 **CLI-Anything** 生成 CLI 的封装规范（「Skill 包装指南」）。  
- 性能与安全 review：路径穿越、命令注入、WS 鉴权。

### Phase D（V1.0+ 预研，不阻塞发布）

- 局域网发现（mDNS）与多设备：此时再评估 **SpacetimeDB** 或继续 **SQLite + 同步协议**。  
- 专利路线：光学推理后端作为 **可选 Provider**，与环境管理器解耦。

## 8. 成功标准（V1.0 验收）

1. 用户用 **自然语言**（非固定口令）发起至少 **2 类** 不同任务，均能生成可读计划并经审批执行。  
2. 所有执行路径写入审计，且可回答「最近一次修改了哪些文件」级别的问题。  
3. 高风险操作 **100%** 走审批或明确策略拒绝。  
4. 新 Skill 可在 **不修改宿主核心代码** 的情况下，仅通过注册 manifest + 二进制/脚本接入（允许宿主提供加载器）。  
5. 有一份面向非开发者的 **安装与卸载/清除数据** 说明。

## 9. 风险与应对

| 风险 | 应对 |
|------|------|
| 通用 Agent 产品功能碾压 | 深耕审计、撤销、权限与本地隐私叙事；开源 Skill 契约 |
| 本地模型能力/速度不足 | 多后端 + 小模型专门做 intent 分类 + 大模型可选 |
| 浏览器与 AGPL 组件合规 | 提前许可证清单；必要时隔离进程与分发方式 |
| 范围蔓延 | 继续以 `mvp_scope` 精神维护「当前版本冻结」，V1.0 单独冻结新文档 |
