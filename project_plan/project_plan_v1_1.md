## 1. 执行摘要

**结论**：项目方向（离线优先、可审批、可审计的个人自动化助手 + Skill 运行时）在 2026 年仍具差异化价值，但需在「环境管理器」层尽快补齐 **真实语言理解/规划**、**Skill 契约与隔离**、**可分发安装形态**，否则易被通用 Agent 框架 + 脚本组合替代。

**战略焦点**：在 V0.5 已验证的「配对 → 计划 → 审批 → 执行 → 审计」闭环上，把 **环境管理器** 做成可扩展内核；软件叙事与 `project_target/patent_1.md` 光学推理路线 **分轨**，通过 **推理后端抽象** 预留未来对接。

**V1.1 侧重**：在 V1.0 工程原则基础上，写清 **大众产品体验** 与 **极简高效工程** 的分工，并把 **Agent 时代特有的安全与生态接口** 提升为与功能并行的交付项。

### 1.1 产品受众与工程哲学（两个维度，不混淆）

#### 用户侧：对标大众

- 安装、配对、对话、计划预览、审批、报错与设置，以 **非技术用户可独立完成** 为验收标准。  
- 信任来自 **看得懂的后果说明**（将动哪些路径、何种风险）与 **可查询的审计**，而非要求用户阅读源码。  
- 一句话对内对齐：**用户侧极简可信赖。**

#### 工程侧：极小依赖、极致效率、AI 原生协作

- **分发体积、冷启动、常驻内存、依赖扇出** 与「隐私、审批、审计」同为长期卖点；须有 **可量化预算与回归手段**。  
- **依赖纪律（核心路径）**：环境管理器、传输协议、持久化与任务状态机等主干优先 **标准库 + 少量可审计依赖**；新增依赖须记录用途、放弃替代方案的理由、移除条件。  
- **代码形态**：不追求「每一位程序员都能轻松读懂全部实现」；优先 **模块边界清晰、契约稳定（类型、schema、协议版本）、测试与 gate 可自动执行**——人类聚焦架构与安全决策，细节迭代由 AI 辅助。对外贡献以 **契约文档 + 关键路径说明** 为主，而非全文教程化。  
- 一句话对内对齐：**工程侧极 lean、面向 AI 协作迭代。**

#### 安全与可审查性（第三维度，衔接上两者）

- 「不必全民读代码」**不等于** 权限、解析外部输入、跨进程边界等 **安全敏感路径** 可以不可审计。  
- 这些模块应对 **核心团队、安全审查与（若开源）社区追责** 保持可读、可测；**终端用户** 仍只通过产品与文档建立信任。

### 1.2 时代与环境下的战略补充（V1.1 汇总提议）

下列项为在 2026 年前后竞争环境下的 **建议性增强**，与 `docs/mvp_scope_v0_5.md` 冻结范围冲突时，以 **单独里程碑 / 下一版本冻结** 纳入，避免拖垮当前闭环。

1. **安全作为产品线的一部分**  
   - Skill **供应链**：签名或哈希锁定、可信更新渠道、可选「仅内置 Skill」模式。  
   - **高危能力默认收紧**：网络、任意命令、递归删除等绑定策略与审批。  
   - **红队用例库**：一批「应拒绝或应二次确认」的场景，与 `docs/weekly_demo_gate.md` 同级进入持续验证（CI 或周期门禁）。

2. **工具协议生态（薄内核、厚适配）**  
   - 行业侧 **MCP 等工具/资源标准** 在普及；建议环境管理器内 **抽象统一「工具调用」接口**，MCP 作为 **可选适配层或独立进程**，避免主干依赖膨胀，与 §1.1 极小依赖原则一致。

3. **模型策略：分层而非单模型**  
   - **小模型或规则**：意图、是否触发审批、简单拒答。  
   - **较大模型**：用于生成计划或解释时，输出 **严格 JSON + schema 校验**，失败则降级或重试，降低「胡编计划」事故面。

4. **可观测性与 AI 迭代配套**  
   - 关键路径（配对、规划、审批、Skill 起停）使用 **稳定事件名** 与可关联 `taskId` 的日志或审计字段，便于 AI 改动后的回归与排障。

5. **对外叙事聚焦一句话**  
   - 在「能跑 Agent」已同质化的环境下，主推例如：**默认不信任、全程可审计的本地执行环境**，并用用户可感知的场景佐证（整理前展示路径、事后可查记录）。

6. **专利与软件**  
   - 光学推理仅通过 **推理后端 Provider** 接入；产品沟通上不绑定「未量产硬件」。

7. **开源、许可与社区（若采用）**  
   - 许可证尽早定型；含 AGPL 等组件时与 **分发形态** 一并设计。  
   - **Skill 规范 + 最小可运行示例** 比长篇架构文更能驱动贡献与 AI 生成合法 Skill。

8. **合规与渠道**  
   - 应用商店上架、隐私政策、区域模型政策等：**本地处理与审计留存** 需在面向用户的说明中可理解陈述；云模型仅作 **可选增强**，与离线承诺一致。

## 3. 与 `project_target/patent_1.md` 的同步分析

### 3.1 专利内容概要

`patent_1.md` 描述的是 **全光大模型计算系统**：多芯光纤空间分复用、权重在光路中循环、微环阵列光计算、色散与信号整形、温漂时序校准等，属于 **AI 推理硬件/光计算** 领域。

### 3.2 与 The Damn Life（软件）的关系

- **技术栈无直接重叠**：当前仓库是编排层、Skill、移动端 UI、SQLite 审计，不涉及光器件或片上光计算。
- **商业/IP 关系**：可作为公司 **第二条能力线**（硬件加速推理）储备；若未来「环境管理器」要调度 **本地光计算推理后端**，可在架构上预留 **推理后端抽象接口**（与今日调度本地 Ollama/vLLM 同类）。
- **申请与产品叙事**：对外产品故事应区分「个人自动化与可信执行环境」与「光学推理加速器」，避免投资人/用户误以为 MVP 依赖未量产硬件。

## 4. 竞品与类似开源/市场格局（定性）

> 下列项目定位来自公开描述；具体指标请以 GitHub/Product Hunt 等实时页面为准。

| 类型 | 代表方向 | 与我们的关系 |
|------|----------|----------------|
| 本地 NL→代码/命令 | Open Interpreter 等 | 功能重叠高；普遍强在执行与生态，弱在「消费级审批/审计/Skill 打包规范」的一体化 |
| IDE/开发者 Agent | Cursor、Codex、各类 agent 框架 | 强在写代码；非「手机控家用电脑 + 非技术用户」场景 |
| 自托管「一个机器人连 Telegram/WhatsApp」类 | 多种开源/发行版（名称与热度变化快） | 渠道多、上手快；往往弱在结构化审计、细粒度文件白名单、可撤销副作用设计 |
| 系统自动化 | Shortcuts、Power Automate、RPA | 成熟但模型与「对话式全权代理」路径不同 |
| 浏览器自动化 | Playwright/Puppeteer + 自研 agent | 与「动态网页」故事重叠；需与安全模型结合 |

**我们的可辩护优势（若坚持做到位）**：

- **人机在环**：高风险默认审批 + 审计时间线，偏「可信个人操作系统」而非「自动跑脚本」。
- **Skill 作为可分发单元**：长期可形成与 CLI/浏览器/文件系统的统一契约（若规范落地）。
- **单机离线闭环**：与强云依赖方案区分（需在产品中真正接上本地模型）。
- **极轻技术栈**：相对「全家桶框架」型助手，更小安装体积、更快启动与更低常驻开销，与本地常驻型产品形态一致（见 §1.1）。

**主要缺陷（当前）**：

- 规划层过简，**泛化 NL 能力不足**，易被「通用 agent + 几条 prompt」替代。
- 尚未形成 **安装即用的终端用户包** 与 **多 Skill 市场/目录**（虽 V0.5 刻意不做市场，但要有技术预留）。
- 浏览器、P2P、多设备均在文档愿景中，**代码未跟上的部分**会削弱差异化叙事。

## 6. 是否值得继续做？如何开展（尤其环境管理器）

### 6.1 价值判断

**值得**，条件是把差异化做成 **默认体验** 而非文档承诺：

1. **可信执行与审计** 与 **自然语言** 同时成立；  
2. **环境管理器** 成为稳定 SDK：第三方 Skill 只靠 manifest + 沙箱边界就能接入；  
3. 至少一条 **非演示级** 场景（文件整理已起步）+ **日程/应用启动** 等第二场景，形成日常习惯。

若长期停留在「关键词 planner + 单 Skill」，则边际价值下降快。

### 6.2 环境管理器（交付定义）

1. **会话与设备**：保留配对与连接抽象，为 V1 局域网预留接口。  
2. **规划器插件化**：规则 planner + **本地/远程 LLM planner** 可切换，输出统一为 **JSON TaskPlan（schema 校验）**。  
3. **策略引擎**：默认拒绝；按 Skill、路径、操作类型（读/写/删/网络）判定是否需审批。  
4. **Skill 运行时**：manifest → 子进程/Docker（择一优先落地）→ 结构化结果 → 审计。  
5. **推理后端抽象**：便于接 Ollama/vLLM 及未来光学推理 **Provider**。  
6. **数据生命周期**：一键清除、导出审计、可选加密备份。

## 7. 路线图（里程碑，V1.1 微调）

在 V1.0 四阶段基础上，**V1.1 嵌入 §1.2 的非功能性工作**（与版本冻结冲突者放入 Phase D 或下一版本）。

### Phase A：内核硬化（约 4–6 周）

- TaskPlan JSON Schema 固定版本；**LLM planner + 规则 fallback**；离线路径清晰。  
- Skill manifest v1；第二个内置 Skill（**应用启动/打开 URL** 或 **最小日程提醒**）。  
- 审计扩展：planner 版本、模型 id、权限决策。  
- Windows 优先的简易打包试点。  
- **V1.1 新增**：初版 **红队用例** 纳入 gate；定义 **包体/启动/内存** 预算的测量方式（可先手工，再 CI）。

### Phase B：体验与信任（约 4–6 周）

- 移动端：计划预览、风险标签、审批说明优化。  
- 撤销：移动/重命名类可逆日志。  
- 可选：**cognee** 类本地知识库（显式目录）。  
- **Lightpanda** spike：只读网页正文（权限开关）。  
- **V1.1 新增**：面向大众的 **安装/卸载/清数据** 文案与流程走查。

### Phase C：生态接口（约 4–6 周，发布候选）

- Skill SDK + 第三方示例 Skill。  
- **CLI-Anything** 包装指南评估。  
- 安全 review：路径穿越、命令注入、WS 鉴权。  
- **V1.1 新增**：**工具调用统一抽象** 与 **MCP 适配** 的技术验证（可不默认随包分发）。

### Phase D（预研，不阻塞发布）

- mDNS / 多设备；**SpacetimeDB** 或 SQLite 同步方案选型。  
- 光学推理 Provider；Skill 签名与 **仅内置 Skill** 模式产品化。

## 8. 成功标准（验收）

### 8.1 V1.0 基线（保留）

1. 用户用 **自然语言**（非固定口令）发起至少 **2 类** 不同任务，均能生成可读计划并经审批执行。  
2. 所有执行路径写入审计，且可回答「最近一次修改了哪些文件」级别的问题。  
3. 高风险操作 **100%** 走审批或明确策略拒绝。  
4. 新 Skill 可在 **不修改宿主核心代码** 的情况下，通过 manifest + 加载器接入。  
5. 面向非开发者的 **安装与卸载/清除数据** 说明。

### 8.2 V1.1 增补（建议纳入同一发布周期或紧随其后的补丁目标）

1. **红队用例集** 在 gate 中全绿或通过豁免流程记录。  
2. **依赖与体积**：主干新增依赖经清单登记；发布物相对基线 **体积/启动** 指标可对比（允许先文档化阈值，再自动化）。  
3. **用户侧**：未读文档即可完成「配对 → 一任务全流程」的可用性自测（小样本即可）。

## 9. 风险与应对（V1.1 扩展）

| 风险 | 应对 |
|------|------|
| 通用 Agent 产品功能碾压 | 审计、撤销、权限与本地隐私叙事；Skill 契约开源 |
| 本地模型能力/速度不足 | 多后端 + 小模型意图 + 大模型可选；严格 schema |
| 浏览器与 AGPL 组件合规 | 许可证清单；进程隔离与分发边界 |
| 范围蔓延 | `mvp_scope` 精神；新能力进 **独立冻结文档** |
| **Skill 供应链与间接注入（V1.1）** | 签名/锁定、来源白名单、红队 gate；用户文件不默认当「可信指令」 |
| **工程可读性与协作（V1.1）** | 契约 + 测试 + 安全模块可读；避免「为路人可读」拖慢 lean 目标 |
