# 逻辑环境与多宿主协作

多设备在用户侧以 **逻辑工作区 / 能力边界** 呈现；不同物理宿主可在同一逻辑流中 **分工协作**。本文档将该产品定调与仓库内模块职责对齐。

## 与核心原则的关系

- **本地优先**：默认算力与数据仍在用户可控的宿主上；跨机协作不改变「数据落点由策略与用户授权决定」的底线。
- **显式权限**：任一宿主参与协作、对外暴露能力或接受远端指令，均须 **可审计、可撤销** 的授权，与现有权限模型一致。
- **强隔离**：Skill / Runtime / 宿主边界不变；协作通过 **受控通道**（中继、事件）完成，不绕过沙箱。
- **事件驱动**：跨宿主协作优先建模为 **事件与编排步骤**（由 `runtime-py` 定义「谁在何种约束下执行哪一步」），而非 UI 直接绑定某台机器。

## 抽象管理 vs 设备列表

| 取向 | 说明 |
| ---- | ---- |
| **默认体验** | 用户操作对象是 **任务、工作区、会话、能力需求**（例如「在受信任环境下完成某条流水线」），而不是「机器 A / 机器 B」清单。 |
| **设备身份** | 物理宿主注册、连接、健康状态仍可能存在（实现上依赖 `relay-go` 等），但 **不作为一级产品叙事**；可收敛在高级视图或运维/调试入口。 |
| **随身设备** | 手机等终端通过 **Web Console 等远程入口** 操作同一逻辑环境（经 `relay-go` 与设备端 Runtime 对话），与「抽象工作区」一致，而非「远程打开某台 PC 的桌面列表」。 |

## 多宿主协作的含义

在统一逻辑工作区内，允许：

- **流水线分阶段**：不同阶段可在不同宿主上执行（例如一端负责采集与预处理，另一端负责重算或仅做审批）。
- **共享逻辑状态**：任务进度、配置意图、审计线索在多端一致（由 `sync-service` 协调，与具体机器解耦）。
- **可达性与会话**：跨端指令与状态推送经 `relay-go` 桥接；编排策略在 `runtime-py`，不在中继层堆业务。

协作关系表达为 **编排与事件契约**（见 `docs/protocols/`），而不是「设备对设备」的特化协议。

## 与仓库模块的对应关系

| 模块 | 在本定调下的角色 |
| ---- | ---------------- |
| `services/relay-go` | 会话与中继、指令转发、多端接入；**不**定义「设备列表 UI」，承载连接与可达性。 |
| `services/sync-service` | 跨端（含多宿主参与时）**任务状态、配置、审计** 的一致性；对齐「一个逻辑环境、多个入口/执行点」。 |
| `services/runtime-py` | AI 与 Skill **编排**；定义步骤、约束与放置策略的抽象层（不将 hostname 当作用户概念）。 |
| `apps/web-console` | 远程控制与审批等；**优先**呈现工作区与任务，而非设备目录。 |
| `apps/app-shell` + `platform/` | 本地宿主与系统能力；作为协作中的 **执行节点之一**，权限本地显式。 |
| `packages/event-contracts`、`docs/protocols/` | 跨模块、跨宿主协作的 **契约与事件** 载体。 |

## Boundaries

- 本文档 **不** 规定具体 API 与事件载荷（见 `docs/api/`、`docs/protocols/`）。
- 本文档 **不** 替代安全威胁模型与权限细则（见 `docs/security/`）。
- 实现阶段的放置策略、冲突解决与故障转移细节，以 ADR 或专项设计补全。
